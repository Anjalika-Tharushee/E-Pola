6. Usability of the Web Application

6.1 Usability Foundations and Operational Context

In Human-Computer Interaction (HCI), usability is defined by ISO 9241-11 as the extent to which a product can be used by specified users to achieve specified goals with effectiveness, efficiency, and satisfaction in a specified context of use [1]. For consumer electronic commerce (e-commerce), usability directly dictates conversion rates, customer retention, and brand trustworthiness [2].

The ePola web application was designed as an accessible electronic marketplace tailored to Sri Lankan retail dynamics ("Pola"), specialized in consumer technology devices spanning three key domains:

  • Computers & Laptops: Business notebooks, ultrabooks, and high-performance gaming laptops (10 devices).
  • Phones & Accessories: Flagships, mid-range smartphones, and budget-friendly devices (10 devices).
  • TV & Home Electronics: Smart displays, cooling appliances, audio hardware, and automated vacuums (10 devices).

By constraining the core catalogue to thirty (30) carefully balanced items, the interface avoids the choice paralysis documented in uncurated marketplaces [2].

6.2 Conceptual Framework and User Mental Models

The design bridges the classic gulf of execution and gulf of evaluation defined by Donald Norman [3]. The gulf of execution is bridged via prominent primary buttons ("Add to cart", "Save to wishlist") and a clear discovery architecture. The gulf of evaluation is addressed through instantaneous visual feedback: dynamic header counters on cart (🛒) and wishlist (♡/♥) icons, real-time price totals in Sri Lankan Rupees (LKR), and inline status messages upon checkout.

6.3 Target User Personas

  • Persona 1 — 'Kavindu' (22, University Student): Highly tech-literate, seeks rapid keyword filtering, compares detailed hardware specs, and requires fast keyboard navigation.
  • Persona 2 — 'Sunethra' (48, Household Consumer): Values high visual legibility, straightforward category cards, transparent local currency prices, and simple cash-on-delivery ordering.
  • Persona 3 — 'Nalaka' (34, Small Electronics Vendor): Requires an intuitive administrative portal to list inventory, adjust stock levels, and review customer orders without database management skills.

7. Requirement Gathering Process

7.1 Methodology and Data Collection

A multi-method requirement gathering investigation was executed comprising:

  1. Semi-Structured Interviews: Eight (8) consumers were interviewed regarding frustrations with existing local portals. Overwhelming feedback highlighted intrusive advertisements, forced registration before seeing cart subtotals, and obscure shipping fees.
  2. Competitive Benchmarking: Evaluation of regional e-commerce portals (Daraz.lk, Singer) indicated that visual density often induces user fatigue [2].
  3. Cognitive Task Walkthroughs: Users exhibited significant drop-off when checkout required more than four screens.

7.2 Functional Requirements (FR)

  • FR1 (Category Discovery): Direct visual entry points for Phones, Computers, and Home Electronics.
  • FR2 (Parametric Search & Filter): Instant real-time keyword search, category selection, and continuous price range sliders.
  • FR3 (Product Inspection): Dedicated views featuring technical specifications, descriptions, and high-resolution visuals.
  • FR4 (Shopping Cart): Live line-item quantity modification, item removal, and instant recalculation of subtotal.
  • FR5 (Cash on Delivery Checkout): Streamlined checkout form capturing delivery data with strict client-side validation.
  • FR6 (Session Management): Demonstration client-side user accounts with SHA-256 password hashing.
  • FR7 (Wishlist Management): LocalStorage-persisted bookmarking of favorite products.
  • FR8 (Seller & Product Administration): Vendor portal for product creation, stock updates, and order tracking.

7.3 Non-Functional Requirements (NFR)

  • NFR1 (Usability & Learnability): First-time visitors shall locate an item and complete a mock order in under 3 minutes.
  • NFR2 (Accessibility): Adherence to W3C WCAG 2.1 Level AA standards for color contrast, keyboard focus, and semantics.
  • NFR3 (Response Latency): UI filtering and page view swaps shall occur in under 50 milliseconds.
  • NFR4 (Zero-Dependency Portability): Runs natively in Chrome, Edge, and Firefox without database configuration.

8. Details and Discussion of Interface Design & Development

8.1 Scenario Description and Customer Journey

The core scenario models a customer seeking a laptop under LKR 250,000. The journey follows four phases:

  1. Discover: Lands on homepage, selects "Computers & Laptops" category card or accesses the shop (`#shop`).
  2. Evaluate: Adjusts price slider to LKR 250,000, reviews Dell Inspiron specs, and saves it to wishlist.
  3. Basket Management: Adds item to cart, increments quantity to 2, and verifies recalculated subtotal in `#cart`.
  4. Checkout: Inputs delivery details in `#checkout` and receives an instant order confirmation (`#order-confirmation`).

8.2 Architectural Implementation and Single Page Routing

Built using pure semantic HTML5, CSS3, and Vanilla JavaScript (ES6+). Navigation is controlled via a single-page hash router (`window.addEventListener("hashchange", renderRoute)`), swapping active `

` containers without network latency.

8.3 State Persistence via Browser Storage

Six local storage structures ensure data persistence across sessions: `pola-cart-v1`, `pola-wishlist-v1`, `pola-users-v1`, `pola-session-v1`, `pola-orders-v1`, and `epola-seller-products-v1`.

8.4 Visual Design System, Typography, and Aesthetics

The interface features an ergonomic dark theme (`--bg-shell: #0b0b0b;`, `--panel: #111111;`) highlighted with fresh organic green (`--accent: #78b82a;`) and warm orange accents (`--orange: #f07a2d;`). High-contrast typography is powered by Google Fonts' "Inter" font family, with explicit `:focus-visible` outlines ensuring keyboard accessibility.

H2: Match between system & real world Marketplace metaphors ("Cart", "Wishlist"); localized LKR currency formatting. 0 Language aligns with real-world consumer mental models.
H3: User control & freedom Direct quantity increment/decrement; one-click item removal; persistent navigation. 1 Users can effortlessly adjust cart quantities or clear search filters.

H8: Aesthetic & minimalist design Curated dark mode; generous white-space; zero intrusive promotional banners. 0 Clean hierarchy directs attention directly toward primary tasks.
H9: Help recognize & recover from errors Descriptive inline error alerts pinpointing missing fields on checkout. 1 Plain language instructions guide users to resolve omissions.
H10: Help & documentation Dedicated About/Contact sections; explicit prototype demo guidance notes. 1 Accessible contact information and clear demo usage disclaimers.

9.2 Empirical Usability Testing with Representative Users

Usability testing was conducted with five (5) participants representing the target demographic, executing four standardized tasks (T1: Filter laptop under LKR 250k; T2: Inspect specs & wishlist; T3: Mutate cart quantity to 2; T4: Complete checkout).

9.3 Quantitative Usability Metrics and SUS Scoring

  • Task Completion Rate (TCR): 95% overall average across all participants.
  • Mean Time on Task (MTT): T1 = 38s, T2 = 24s, T3 = 19s, T4 = 47s.
  • Single Ease Question (SEQ): Average score of 6.6 / 7.0.
  • System Usability Scale (SUS): Average composite score of 84.5 / 100, earning an "A - Excellent" rating [4].

11. Other Information

11.1 Client-Side Execution and Zero-Dependency Architecture

The ePola architecture executes completely client-side. Opening `index.html` directly in any web browser loads all routes, scripts, styles, and images without external runtime installations.

11.2 Security, Data Privacy, and Password Hashing

Demo user authentication uses the native Web Cryptography API (`crypto.subtle.digest`) to hash passwords with SHA-256 and unique cryptographic salts before storing them in `localStorage`.

11.3 Limitations and Recommendations

Browser `localStorage` is restricted to ~5MB. In future production revisions, integrating a remote RESTful backend with IndexedDB caching and multi-language support (Sinhala, Tamil, English) is recommended.
